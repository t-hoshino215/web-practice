# Common Coding Style Rules

共通のコーディング規約

## 前提

フォーマット・リンティング・型チェックは自動化ツールに任せる。（例: Prettier, ESLint, Ruff）
このファイルは、ツール検出できない判断基準を定義する。

## Immutability (不変性)

常に新しいオブジェクトを作成し、既存のオブジェクトを変更しないこと:

```text
// Pseudocode
WRONG:  modify(original, field, value) → 元のオブジェクトをインプレースで変更する
CORRECT: update(original, field, value) → 変更を加えた新しいコピーを返す
```

理由: 不変なデータは隠れた副作用を防止し、デバッグを容易にし、安全な並行処理を可能にする。

## File Organization (ファイル構成)

多くの小さなファイル > 少ない大きなファイル:

- 高凝集・低結合を維持する
- 200-400行が目安、最大800行
- 大きなモジュールからユーティリティを抽出する
- 機能やドメイン別に整理する

## Error Handling (エラーハンドリング)

エラーを包括的に処理すること:

- すべてのレベルで明示的にエラーを処理する
- UI向けコードではユーザー向けの分かりやすいエラーメッセージを提供する
- サーバー側では詳細なエラーコンテキストをログに記録する
- エラーを黙って無視しない

## Input Validation (入力検証)

システムの境界では必ず検証する:

- すべてのユーザー入力を処理する前に検証する
- スキーマベースの検証を使用する
- 明確なエラーメッセージで早期に失敗する（Fail Fast）
- 外部データ（APIレスポンス、ユーザー入力、ファイル内容）を信用しない

## Commenting (コメント)

コードの意図を説明するためのコメントを記載する:

- なぜこのコードが必要なのか（WhatではなくWhy）
- 外部仕様・API の制約など、コードから読み取れない前提条件
- 一時的な対処や恒久対応への言及

## Code Quality Checklist (コード品質チェックリスト)

作業完了前に確認:

- [ ] コードは読みやすく、適切に命名されている
- [ ] 関数が適切な粒度（<50行）
- [ ] ファイルが焦点を絞っている（<800行）
- [ ] 深いネストがない（>4階層）
- [ ] エラーが明示的に処理されている
- [ ] ハードコードされた値がない（定数や設定を使用し、秘密情報や認証情報を含んでいない）
- [ ] `console.log` やデバッグ用コードが残っていない
- [ ] ミューテーションがない（不変パターンが使用されている）
- [ ] 新機能に対するテストが存在する

例外を許容する場合は、理由を明確にし、ユーザーに確認する。

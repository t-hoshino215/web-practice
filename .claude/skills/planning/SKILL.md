# Planning skill

エキスパートのプランニングスペシャリストとして包括的で実行可能な実装計画を作成する。

## 役割

- 計画プロセスに沿って、要件を分析し詳細な実装計画を作成する
- 複雑な機能を管理しやすいステップに分解する
- 依存関係や潜在的なリスクを特定する
- 最適な実装順序を提案する
- エッジケースやエラーシナリオを考慮する

## 計画プロセス

### Step 1: 現状のアーキテクチャレビュー

1. リクエストに関連するファイルを `Glob` と `Grep` で特定する
2. 関連コードを `Read` して既存の実装パターン・テスト方針を理解する
  - 既存のコードベース構造を分析する
  - 影響を受けるコンポーネントを特定する
  - 類似の実装を確認する
  - 再利用可能なパターンを検討する

### Step 2: 要件の整理と確認

- 機能要求を完全に理解する
- 作業スコープ・成功基準・完了条件を特定する
- 前提条件と制約を列挙する
- 必要に応じて、ユーザーに確認のための質問をする

#### ユーザーへの質問

ユーザーへ質問する場合は、下記の形式で不明点や曖昧な点を明確にするための質問を1問ずつ行う。

```text
# 確認事項

## Q1. 使用するデータベースはどれですか？
- 背景: スキーマ設計に影響するため
- [ ] PostgreSQL
- [ ] SQLite
- [ ] MySQL
- [ ] その他（自由記載）
```

### Step 3: ステップ分解

以下を含む詳細なステップを作成する：

- 明確で具体的なアクション
- ファイルパスや場所
- ステップ間の依存関係
- 想定される複雑さ
- 潜在的なリスク

### Step 4: 実装順序

- 依存関係に基づいて優先順位を付ける
- 関連する変更をグループ化する
- コンテキストスイッチを最小限に抑える
- 段階的なテストを可能にする

### Step 5: 実装計画の作成

- 後述の計画フォーマットを埋め、ユーザーの承認を得る。
- ユーザーの承認を得たら、実装計画書として保存する。
  - 保存先ディレクトリ: `docs/plans/`
  - ファイル名: `YYYYMMDD-HHMMSS_{機能名}.md`
  - {機能名} は、実装する機能名を英子文字のケバブケースで表す（例: `user-oauth2-auth`, `search-api-pagination`）

## 計画フォーマット

```markdown
# 実装計画: [機能名]

## 概要

[2〜3文の要約]

## 要件

- [要件1]
- [要件2]

## 影響範囲

| ファイルパス | 変更種別 | 変更内容の概要 |
| --- | --- | --- |
| `path/to/file.py` | 修正 | 〜の処理を変更 |
| `path/to/new.py` | 新規 | 〜を追加 |
| `path/to/test.py` | 修正 | テストケースを追加 |

## 実装ステップ

### フェーズ1: [フェーズ名]

1. **[ステップ名]*- (ファイル: path/to/file.xx)
  - アクション: 実施する具体的な内容
  - 理由: このステップが必要な理由
  - 依存関係: なし / ステップXが必要
  - リスク: 低 / 中 / 高

2. **[ステップ名]*- (ファイル: path/to/file.xx)
  ...

### フェーズ2: [フェーズ名]
...

## テスト戦略

- ユニットテスト: [テスト対象ファイル]
- 統合テスト: [テスト対象のフロー]
- E2Eテスト: [テスト対象のユーザージャーニー]

## リスクと対策

- **[リスク名]**: [説明]
  - 対策: [対応方法]

## 成功基準・完了条件

- [ ] 基準・条件1
- [ ] 基準・条件2
```

## ルール

1. **具体的に書く**: 正確なファイルパス、関数名、変数名を使用する
2. **エッジケースを考慮する**: エラー、null値、空状態を想定する
3. **変更を最小限にする**: 書き換えよりも既存コードの拡張を優先する
4. **パターンを維持する**: 既存プロジェクトの規約に従う
5. **テスト可能にする**: テストしやすい構造にする
6. **段階的に考える**: 各ステップが検証可能であること
7. **意思決定を記録する**: 「何を」だけでなく「なぜ」を説明する
8. **コードの変更はしない**: このスキルではコードの作成・修正は行わない

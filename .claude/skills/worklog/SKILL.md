# Worklog（作業ログ）スキル

実装・修正が完了した後に、何が変わったかを正確に記録し、チームや将来の自分が振り返れる **構造化された作業ログ** を作成する。

---

## ワークフロー

### Phase 1: 情報収集

以下のソースから作業内容を収集する。

#### 1.1 Git 履歴の収集

```bash
# 直近のコミット履歴（デフォルト: 最新20件、または直近24時間）
git log --oneline --since="24 hours ago"

# もしコミットがなければ範囲を広げる
git log --oneline -20

# 各コミットの詳細な変更統計
git log --stat --since="24 hours ago"

# 未コミットの変更
git diff --stat
git diff --cached --stat
```

引数でタスク説明やコミット範囲が指定されている場合は、そちらを優先する。
例: `/log abc1234..HEAD` → 指定範囲のコミットを対象にする。

#### 1.2 変更ファイルの分析

```bash
# 変更されたファイル一覧
git diff --name-status HEAD~N  # N はコミット数に応じて調整

# ファイル種別ごとの変更量
git diff --stat HEAD~N
```

変更ファイルを以下のカテゴリに分類する:

- **ソースコード**: 実装の本体
- **テスト**: テストファイル
- **設定・構成**: 設定ファイル、CI/CD、依存関係
- **ドキュメント**: README、docs/ 以下のファイル

#### 1.3 関連ドキュメントの参照

`docs/plans/` に関連する計画書があれば Read で参照し、ログに紐づける。
ファイル名の日付やキーワードからコミット内容との関連を推定する。
完全一致しなくても、内容が関連していれば紐づける。

#### 1.4 計画との差分（任意）

関連する変更計画書が見つかった場合、計画と実際の実装を比較する:

- 計画通りに実施されたステップ
- 計画から変更・追加されたこと
- 未実施のステップ（あれば）

### Phase 2: 作業ログの生成

収集した情報をもとに、後述の出力フォーマットで作業ログを作成し、Markdown ファイルとして出力する。

1. 計画書を `docs/logs/YYYYMMDD-HHMMSS_<内容>.md` として保存する
  - リクエスト内容から英語ケバブケースのファイル名を生成
  - `Write` ツールでファイルに書き込む
2. 保存完了後、保存先パスを含めてユーザーに報告する

## 出力フォーマット

計画書は **必ず** 下記のフォーマットで出力する。
セクションを省略してはならない。該当しない場合は「なし」と記載する。

```Markdown
# 作業ログ

## 1. 概要

| 項目 | 内容 |
| ----------- | ------ |
| 日付 | YYYY-MM-DD |
| タスク | （作業内容を1行で要約） |
| ステータス | 完了 / 一部完了 / 進行中 |
| 関連ドキュメント | （要件定義書・設計書・計画書へのパス。なければ「なし」） |

## 2. 作業サマリー

（何を行ったかの概要。2〜5文程度で、技術的な背景を知らない人にも伝わるように書く）

## 3. 変更内容

### コミット履歴

| コミット | メッセージ | 変更ファイル数 |
| --------- | ---------- | ------------- |
| `abc1234` | feat: ○○を追加 | 3 files |
| `def5678` | fix: △△を修正 | 1 file |
| `ghi9012` | test: □□のテストを追加 | 2 files |

### 変更ファイル一覧

| カテゴリ | ファイルパス | 変更種別 | 概要 |
| --------- | ------------ | --------- | ------ |
| ソースコード | `src/auth/oauth.py` | 新規 | OAuth2 認証モジュール |
| ソースコード | `src/auth/handler.py` | 修正 | 認証ハンドラに OAuth2 フローを追加 |
| テスト | `tests/auth/test_oauth.py` | 新規 | OAuth2 のユニットテスト |
| 設定 | `pyproject.toml` | 修正 | 依存ライブラリ追加 |

### 変更の詳細

（主要な変更について、何をどう変えたかを簡潔に説明。
  コードの詳細には踏み込まず、「何のために何をしたか」のレベルで記述する）

#### （変更1のタイトル）

- （説明）

#### （変更2のタイトル）

- （説明）

## 4. 計画との対比

（関連する変更計画書がある場合のみ記載）

| 計画のステップ | ステータス | 備考 |
| ------------- | ---------- | ------ |
| Step 1: ○○ | ✅ 完了 | （差異があれば記載） |
| Step 2: △△ | ✅ 完了 | 計画通り |
| Step 3: □□ | ⏳ 未着手 | 次のタスクで実施予定 |

## 5. 技術的メモ

（実装中に気づいたこと、ハマったポイント、将来の参考になる情報。
  なければ「なし」。以下は記載すべき内容の例）

- 設計判断: （なぜこの実装方法を選んだか）
- ワークアラウンド: （一時的な対処をした場合、その理由と恒久対応の方針）
- パフォーマンス: （パフォーマンスに影響する変更をした場合）
- 依存関係: （新しいライブラリを追加した場合、選定理由）

## 6. 残課題

| 課題 | 優先度 | 備考 |
| ------ | ------- | ------ |
| （残っている課題） | 高/中/低 | （補足情報） |

```

### ファイル命名規則

```text
docs/logs/YYYYMMDD-HHMMSS_<内容>.md
```

- `YYYYMMDD`: 作成日
- `HHMMSS`: 作成時間
- `<内容>`: リクエスト内容を表す短い英語ケバブケース（例: `add-oauth2-auth`, `refactor-db-layer`）
- 日本語のリクエストでも **ファイル名は英語** にする
- `docs/logs/` ディレクトリが存在しなければ `mkdir -p` で作成する

**例:**

- OAuth2 認証の実装作業 → `docs/logs/20260407-102315_implement_oauth2_auth.md`
- 検索ページネーションのバグ修正 → `docs/logs/20260407-102315_fix_search_pagination.md`
- DB層リファクタリング → `docs/logs/20260407-102315_refactor_db_access_layer.md`

## ガイドライン

### コミット範囲の決定

引数でコミット範囲が指定されていない場合、以下の優先順位で対象範囲を決める:

1. 引数でコミット範囲が指定されている → その範囲（例: `abc1234..HEAD`）
2. 引数でタスク説明がある → 直近24時間のコミットから関連するものを抽出
3. 引数なし → 直近24時間のコミット全体。コミットがなければ直近20件

### 粒度の調整

- **コミット数 1〜3**: 変更の詳細セクションを丁寧に記述
- **コミット数 4〜10**: 主要な変更にフォーカスし、軽微な修正はまとめる
- **コミット数 11以上**: カテゴリ別に要約し、個々のコミット詳細は省略

### やるべきこと

- git の情報を **正確に** 反映する（コミットハッシュ、ファイルパス、変更統計）
- 「何をしたか」だけでなく「なぜしたか」も可能な限り記録する
- 関連ドキュメント（要件定義書、設計書、計画書）があれば必ず紐づける
- 未完了のタスクがあれば「残課題」に明記する

### やってはいけないこと

- コードの変更を行う（ログの Write のみ許可）
- git 履歴を改変する
- 存在しないコミットやファイルを記載する
- 機密情報（APIキー、パスワード等）をログに含める
- ファイル名に日本語やスペースを使う
